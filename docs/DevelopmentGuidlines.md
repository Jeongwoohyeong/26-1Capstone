# 통합 개발 지침

## 1. 개발 프레임워크

### 1.1 결정 내용
- **UI**: React
- **DB**: SQLite
- **분석**: Python

### 1.2 선정 이유
- UI는 빠른 화면 구성과 높은 자유도를 고려하여 React를 사용한다.
- DB는 오프라인 환경과 단순한 배포를 고려하여 SQLite를 사용한다.
- 분석 로직은 데이터 처리와 계산에 유리한 Python을 사용한다.

### 1.3 비고
- 세부 라이브러리 선정은 이후 구현 과정에서 추가로 논의한다.
- UI, DB, 분석 간 데이터 전달 방식은 추후 상세 설계에서 구체화한다.

## 2. 코딩 컨벤션

### 2.1 목적
본 프로젝트의 코딩 컨벤션은 팀원 간 코드 스타일을 통일하여 가독성과 협업 효율을 높이기 위해 정한다.  
세부 규칙은 회의 후 최종 합의에 따라 보완한다.

### 2.2 기본 원칙
- 코드는 **일관성 있게 작성**한다.
- 변수, 함수, 클래스 이름은 **의미가 드러나도록 작성**한다.
- 언어가 다르더라도 **프로젝트에서 사용하는 용어는 최대한 통일**한다.
- 본 프로젝트는 소규모 대학 과제이므로 협업 효율을 위해 **JavaScript와 Python의 변수명/함수명 표기법을 camelCase로 통일**한다.

### 2.3 JavaScript 명명 규칙
- **컴포넌트명 / 클래스명**: `PascalCase`
- **변수명 / 함수명**: `camelCase`
- **상수명**: `UPPER_SNAKE_CASE`

#### 예시

```js
const MAX_BATCH_SIZE = 8;
const selectedFiles = [];

function parseExcelFiles() {}

class FileParser {}

function UploadPanel() {
  return null;
}
```

### 2.4 Python 명명 규칙
- **클래스명**: `PascalCase`
- **변수명 / 함수명**: `camelCase`
- **상수명**: `UPPER_SNAKE_CASE`

#### 예시

```python
MAX_BATCH_SIZE = 8
selectedFiles = []

def parseExcelFiles():
    pass

class FileParser:
    pass
```

### 2.5 변수 / 함수 / 클래스 명명 원칙
- **변수명은 명사형**으로 작성한다.  
  예: `selectedFiles`, `normalizedData`
- **함수명은 동사형**으로 작성한다.  
  예: `parseExcelFiles`, `saveNormalizedData`
- **클래스명은 역할이 드러나는 명사형**으로 작성한다.  
  예: `FileParser`, `DataRepository`
- **상수는 모두 대문자**로 작성한다.  
  예: `MAX_BATCH_SIZE`, `MIN_IRRADIANCE_VALUE`
- **boolean 변수는 상태가 드러나는 이름**으로 작성한다.  
  예: `isLoading`, `hasError`, `canUpload`

### 2.6 축약어 사용 규칙
- 의미가 불분명한 **임의 축약은 사용하지 않는다.**
- 이름은 가능하면 **풀어서 작성**한다.
- 다만 널리 통용되는 약어는 허용할 수 있다.  
  예: `id`, `url`, `api`, `db`, `ui`, `iv`, `stc`

#### 예시
- 권장: `maxFileSize`, `selectedFiles`, `normalizedData`
- 비권장: `maxSz`, `selFiles`, `normData`

## 3. 커밋 메시지 컨벤션

### 3.1 목적
본 문서는 팀 프로젝트에서 사용할 커밋 메시지 작성 기준을 간단히 정리하기 위한 초안이다.  
세부 규칙은 회의 후 최종 합의에 따라 보완한다.

### 3.2 커밋 타입
- `feat`: 신규 기능 개발
- `refactor`: 기능 동작 변화 없이 구조를 개선한 경우
- `fix`: 버그 및 오류 수정
- `chore`: 설정, 문서, 폴더 정리 등 기타 작업
- `WIP`: 작업 중인 내용으로, 아직 완료되지 않은 중간 작업

### 3.3 작성 원칙
- 커밋 메시지는 **무엇을 했는지 드러나게 작성**한다.
- 제목은 **간단하고 명확하게 작성**한다.
- 제목만으로 설명이 부족하면 본문에 추가 작성한다.
- 하나의 커밋에는 가능하면 **하나의 작업 내용만 포함**한다.

### 3.4 예시
- `feat: 엑셀 파일 업로드 기능 추가`
- `feat: I-V 커브 시각화 컴포넌트 추가`
- `fix: 파일 확장자 검증 오류 수정`
- `refactor: 파싱 로직 함수 분리`
- `chore: 초기 프로젝트 구조 정리`
- `WIP: 다중 파일 업로드 화면 작업 중`

### 3.5 참고 사항
- 사용자 입장에서 새로운 기능이 추가된 경우에는 `feat`를 사용한다.
- 기능 변화 없이 내부 코드 구조만 정리한 경우에는 `refactor`를 사용한다.
- 버그 수정이나 오작동 해결은 `fix`를 사용한다.
- 설정 파일 수정, 문서 작성, 기타 정리 작업은 `chore`를 사용한다.
- 아직 완료되지 않은 중간 작업을 임시로 기록할 때는 `WIP`를 사용한다.

## 4. 협업 방식 및 역할 분담

### 4.1 팀 구성
- 팀원은 총 3명으로 구성한다.
- 역할 분담은 다음과 같다.
  - **UI**: 우형
  - **DB**: 소윤
  - **분석**: 정우

### 4.2 협업 원칙
- 각자 담당 영역을 우선적으로 개발하되, 기능 연결 지점은 사전에 공유한다.
- 공통으로 사용하는 데이터 구조, 파일 형식, 테이블 정의는 팀 내 합의를 거쳐 확정한다.
- 구현 중 문제가 발생하면 혼자 오래 붙잡기보다 진행 상황과 막힌 지점을 공유한다.

### 4.3 문제 상황 공유 원칙
문제 상황을 공유할 때는 아래 내용을 함께 전달한다.
- 현재 무엇을 개발 중인지
- 어디에서 막혔는지
- 어디까지 시도했는지
- 필요한 도움이 무엇인지

#### 예시
- “엑셀 파싱 중 특정 시트 구조 대응에서 막혔음”
- “날짜 컬럼 파싱 방식을 2가지 시도했지만 형식이 일정하지 않아 실패함”
- “raw data 샘플 추가 확인이 필요함”

## 5. 브랜치 전략 및 Git 운영 방식

### 5.1 브랜치 구성
본 프로젝트는 아래와 같이 브랜치를 운영한다.
- `main`: 최종 통합 브랜치
- 개인 작업 브랜치 3개
  - 예: `feature/ui-woohyeong`
  - 예: `feature/db-soyoon`
  - 예: `feature/analysis-jeongwoo`

### 5.2 운영 원칙
- 각 팀원은 자신의 작업 브랜치에서 기능을 개발한다.
- 검토 및 테스트 후 `main` 브랜치에 반영한다.
- 직접 `main`에서 작업하지 않는다.
- 큰 기능은 가능한 한 작은 단위로 나누어 커밋한다.

### 5.3 병합 전 확인 사항
- 실행 오류가 없는지 확인한다.
- 기존 기능에 영향이 없는지 확인한다.
- 커밋 메시지가 컨벤션을 따르는지 확인한다.
- 불필요한 파일이 포함되지 않았는지 확인한다.

## 6. 데이터 기준 및 분석 규칙

### 6.1 주요 데이터 항목
본 과제에서 우선적으로 다루는 항목은 다음과 같다.
- I-V 커브
- 일사량
- 모듈 온도(T3 기준)

### 6.2 정규화 기준
- 정규화는 **IEC 60891:2021 기반 STC 기준 전력값**을 따른다.
- KS 버전은 국제 표준의 번역본으로 이해한다.
- 정규화 결과는 후속 분석 및 비교를 위해 DB에 저장한다.

### 6.3 데이터 수집 특성
- 데이터는 실시간 수집이 아니다.
- 필요 시 엑셀 파일을 받아 파싱 후 DB화한다.
- 데이터는 20분마다 수집된다.
- 채널마다 기준 모듈 온도가 다를 수 있다.
